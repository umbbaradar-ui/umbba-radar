## 왜 2계정 (스케일 방식)
한 계정에 양/빈도를 올리면 차단만 빨라진다(검증됨: 80×5×5 즉시밴, 40×3도 플래그계정은 막힘).
정석은 **부하 분산** — 여러 더미계정이 471개 타겟을 나눠 스캔, 계정당 부하는 안전선 유지.
- 타겟 분배는 **자동**: `last_scanned_at` 오래된 순으로 집으므로, 계정2를 계정1 직후(시차)에
  돌리면 자동으로 다른 슬라이스를 스캔. 수동 배정 불필요.

## 기술 셋업 (cookies2.txt 준비되면 Claude가)
- `scan2.bat` (준비됨): `set UMBBA_COOKIES_FILE=cookies2.txt` → 둘째 쿠키 사용(프로세스 env가 .env보다 우선, override=False 확인됨). 로그는 `scan2-log.txt` 분리.
- 스케줄러: `엄빠레이더-스캔2` 작업, 트리거 시차(계정1 회차 +15분), 워밍업 단계마다 `--max-accounts` 상향.
- 타겟 목록(471개)·`last_scanned_at`는 공유 → 자동 슬라이스 분배.

## 지표·체크포인트 (언제 ramp / 언제 중단)
- 측정: `node tools/diag-pipeline.mjs` + scan2-log의 `HttpError` 수 + 계정 생존일수
- **ramp 조건**: 직전 단계 며칠간 scan2-log에 차단(HttpError/login) 0 → 다음 단계로
- **중단/백오프**: scan2-log에 차단 뜨면 → 계정2 스캔 멈춤. 워밍업 더 하거나(며칠) 계정이 burned면 폐기→새로.
- 한 계정 막혀도 나머지로 버팀(분산의 장점).

## 주의
- ⚠️ **워밍업 건너뛰면 새 계정도 며칠 만에 밴.** Day1~3 수동 사용 필수.
- ⚠️ **2번이 1번 불안정을 고쳐주지 않음.** 1번도 이번 휴식 후 안정 확인이 전제(Day1~3 병행 관찰).
- 쿠키 2배 관리(둘 다 만료/차단 시 각각 갱신). 막히면 텔레그램 알림 → 인증 풀기 사이클.
- (후속) run-b.ps1 헬스리포트는 현재 scan-log.txt만 읽음 → 계정2 결과까지 보려면 scan2-log도 합산하도록 보강 예정.

## 장기 (병행 권장)
IG 스크래핑은 본질적으로 두더지잡기. 출시 안정성의 진짜 보험은 **비-IG 소스**(사용자 제보/submit·공공데이터·체험단 플랫폼). IG는 "보너스 소스", 백본은 다변화.
