## 0. 결론 먼저 (3줄)

1. **보고서의 방향(유틸리티 툴 / 아웃링크 클릭이 핵심가치 / B2B 종착지)은 맞다.** 데이터가 뒷받침한다 — 로그인 유저 원문 CTR **48%**, 상위 유저는 6주간 21·15·10·9일 재방문. **콘텐츠-시장 적합은 이미 증명됐다.**
2. **그런데 KPI 순서가 틀렸다.** 보고서는 1단계를 "D7 리텐션 25%"로 잡았는데, 지금 병목은 리텐션이 아니라 **모수 생성**이다. 최근 9일 익명 방문자 32명 중 가입 시도 **1명(3%)**, 신규 자녀등록 **주 1~2명**. 리텐션을 잴 사람이 안 만들어지고 있다.
3. **인스타 연동 등급제는 기술적으로 불가능에 가깝고**(§6-1), 그 대안으로 검토한 "카드 조건 기반 핏 태그"도 **캡션 전수조사 결과 폐기**했다(§6-3 — 팔로워 조건 명시 361건 중 **2건**). 대신 진짜 결론은 §6-3b: **조건이 공개되지 않는 시장이므로 제품 축이 "고르기"가 아니라 "놓치지 않기"** 다. 이건 이미 만든 기능(관심·마감·푸시)을 두껍게 하는 방향이라 신규 개발이 거의 없다.
4. **지표가 죽어 보이는 것 중 일부는 계측 착시다.** `/admin/users`의 "최근 로그인"은 방문이 아니라 인증을 재고 있어, **살아있는 유저 6명이 "2개월째 휴면"으로 표시**되고 있었다(§4-1b).

## 3. KPI 재설계

### 3-1. 북극성 지표 (NSM) — **주간 유효 발견자 (WQD)**

> **WQD = 그 주에 `source_link_click`(원문 이동)을 1회 이상 한 고유 유저 수**

왜 이것인가:

- 도달 × 가치전달을 **한 숫자**로 압축 (카드를 봤다 ≠ 가치를 받았다. 밖으로 나가야 가치)
- **카운트형**이라 성장과 함께 커진다 (비율형은 유저 10명일 때가 더 좋게 나오는 함정)
- 나중에 **광고주에게 파는 숫자와 정확히 같다**

**현재값:**

| 주차 | WAU | **WQD** | 비율 |
|---|---|---|---|
| 07-06 | 10 | 7 | 70% |
| 07-20 | 29 | 10 | 34% |
| 08-03 | 50 | 17 | 34% |
| 08-10 | 32 | 6 | 19% |
| 08-17 | 15 | **6** | 40% |

→ **지금 WQD ≈ 주 6~17명.**

### 3-2. 단계는 '개월'이 아니라 '관문(Gate)'으로

보고서는 1~3개월차 / 4~6개월차로 나눴는데, 실제로는 이미 런칭 3개월인데 MAU 30이다. 시간이 아니라 **통과 조건**으로 나눠야 한다.

| 관문 | 통과 조건 (AND) | 통과하면 하는 일 |
|---|---|---|
| **G0 — 지금**<br>"모수 만들기" | ① **WQD 30명/주**<br>② 방문→자녀등록 전환 **10%**<br>③ 푸시 옵트인 **30%** | 리텐션 최적화로 이동 |
| **G1 — 습관** | ① WQD **200명/주**<br>② 로그인유저 **W4 리텐션 30%**<br>③ 푸시 오픈율 15% | 수익화 준비·사업자등록 |
| **G2 — 수익** | ① WQD **1,000명/주**<br>② 세그먼트당 최소 300명 | B2B 대시보드 착수 |

> **G0을 통과하기 전엔 리텐션 목표를 KPI로 쓰지 말 것.** 지금 리텐션 수치는 n이 작아 노이즈다.

### 3-3. L1 입력지표 4개 (매주 이것만 본다)

| # | 지표 | 정의 | 현재 | G0 목표 |
|---|---|---|---|---|
| A | **획득** | 주간 신규 방문자(첫 `app_open`) | 미계측 | 주 100명 |
| B | **활성화** ★ | 방문 → **자녀등록 완료** 전환율 | **~3%** | **10%** |
| C | **가치** | 활성유저 원문 CTR | 로그인 48% / 익명 19% | 로그인 45% 유지 |
| D | **유지** | 로그인유저 W1 / W4 코호트 잔존 | W1 ~64%(2일+) | W4 30% |

**지금 가장 급한 건 B다.** C는 이미 목표 초과 달성(48% >> 15%), A와 B가 0에 수렴 중.

### 3-4. 보조지표 (진단용, KPI 아님)

- **공급건강**: 일 발행수 / **매칭 커버리지** = "자녀 등록자 중 오늘 맞춤카드 1건 이상 있는 비율" → **100% 나와야 정상.** 하나라도 0이면 그 유저는 이탈 확정
- **푸시**: 옵트인율 / 발송당 오픈율 / 옵트아웃율
- **품질**: 카드당 원문클릭(카드 랭킹) / AI skip률 / 반려율
- **표면(surface)**: twa / pwa / browser 별 전환·리텐션 (commit `41594dc`로 계측 시작됨)

## 4. DAU / WAU / MAU — 어떻게 관리할 것인가

### 4-1. 먼저 **정의**를 못 박아야 한다 (지금 숫자를 못 믿는 이유)

| 항목 | 지금 상태 | 바꿀 것 |
|---|---|---|
| **Active의 정의** | "카드를 클릭한 사람"만 잡힘 | `app_open` 1건 = Active. **열고 3초 보고 나간 사람 = 가장 중요한 이탈 신호인데 지금 통째로 안 보임** |
| **날짜 경계** | `Date.now() - N*24h` 롤링 (`repository.ts:195`) | **KST 00:00 기준 일자**로 고정 (롤링은 코호트·요일 패턴을 못 봄) |
| **사람 단위** | `user_id` 우선, 없으면 `anon_id` (`repository.ts:291`) | 동일. 단 로그인 시 **`identify` 이벤트로 anon_id ↔ user_id 스티칭** → 같은 사람 2중 카운트 제거 |
| **내부 트래픽** | 제외 없음 | 관리자 user_id + `?internal=1` 플래그 → 통계에서 제외 |

### 4-1b. ⚠️ `/admin/users`의 "최근 로그인"은 리텐션 지표가 아니다 (2026-08-20 확인)

**증상:** `/admin/users`를 보면 최근 로그인이 가장 빠른 게 7일 전이고 32명 중 27명이 30일+ → "유저가 다 죽었다"로 읽힘.

**원인:** `last_sign_in_at`은 **실제 인증(로그인) 시점만** 기록한다.
Supabase의 refresh token 갱신으로 세션이 이어질 때는 **갱신되지 않는다.**
즉 6/25에 카카오로 로그인하고 세션 유지된 채 어제까지 쓴 유저는 이 값이 **6/25에 멈춰 있다.**

**실측 대조 — 8/14 이후 활동한 로그인 유저 6명 전원이 이 경우:**

| user_id | last_sign_in_at | **실제 마지막 활동(events)** | 괴리 |
|---|---|---|---|
| e1198901 | 06-25 | **08-20** | 56일 |
| ff7e4cee | 07-02 | **08-20** | 49일 |
| 36d6bfc4 | 06-25 | **08-19** | 55일 |
| bd4f7a8a | 06-29 | **08-18** | 50일 |
| fa618ce8 | 06-25 | **08-16** | 52일 |
| d5034ce4 | 06-25 | **08-15** | 51일 |

**고칠 것:**

- `/admin/users`의 컬럼명 "최근 로그인" → **"최근 인증"** (`UserRow.tsx:133`)
- 그 옆에 `events` 기반 **"최근 방문"** 컬럼 신설 ← 이게 진짜 리텐션 지표
- 리텐션·휴면 판정은 **무조건 events 기준**. `last_sign_in_at`은 OAuth 재인증 진단용으로만.

> **교훈:** 지표가 이상하면 유저를 의심하기 전에 **그 컬럼이 뭘 재는지**부터 확인. 이번 건은 하마터면 "테스터 전멸"로 오판할 뻔했다.

### 4-2. 추가할 이벤트는 **3개뿐** (반나절 작업)

```
1) app_open   — 세션당 1회(sessionStorage 가드) + surface  → 진짜 DAU/WAU/MAU
2) identify   — 로그인 성공 시 { anon_id, user_id }        → 중복 제거 + 익명기간 소급 귀속
3) feed_empty — 맞춤 결과 0건 노출 시 { stage }            → 1회 이탈 원인 1순위 후보 검증
```

> **이걸 먼저 하지 않으면 §5의 개선을 해도 효과를 측정할 수 없다.** 그래서 0순위.

### 4-3. **규모별로 보는 지표가 다르다** (이게 핵심)

| 규모 | 볼 것 | 보지 말 것 |
|---|---|---|
| **지금 (WAU < 100)** | **주차별 코호트 표**(가로=가입주차, 세로=W0~W4 잔존) + WQD 절대수 + 퍼널 5칸 | DAU/MAU 비율 — 1명이 3%p를 움직여서 의미 없음. D7 리텐션도 마찬가지 |
| **WAU 100~500** | DAU/WAU 추가 (**목표 25~30% = 주 1.8~2.1일**) + 표면별 리텐션 | 여전히 MAU 헤드라인 |
| **MAU 500+** | DAU/MAU 스티키니스 (**목표 15~20%**) + L28 곡선 + 리텐션 평탄화 여부 | |

> **보고서의 "DAU/WAU 40%"는 주 2.8일 방문이다.** 마감이 계속 도는 체험단 앱이라 이론상 불가능은 아니지만, 현실적 상한이므로 목표가 아니라 **천장**으로 두는 게 맞다. 실무 목표는 **DAU/WAU 30%**.

### 4-4. 리텐션은 **두 개로 쪼개서** 본다

- **로그인 유저 리텐션** = 진짜 신호. (현재 22명 중 14명이 2일+ 재방문 = 64%)
- **전체(익명 포함) 리텐션** = anon_id 소멸 때문에 **구조적으로 과소**. 추세만 보고 절대값은 믿지 말 것.

### 4-4b. 영역·자리별 성과(`card_open`) — 광고 인벤토리의 근거 ✅ 2026-08-20 적용

기존 `card_click`은 **상세 페이지 마운트 시점**에 찍혀서 "어디서 눌러 들어왔는지"를 몰랐다.
→ `CardSlot` 래퍼로 클릭 지점에서 `card_open`{zone, position, list_len}을 별도 기록.
(`card_click`은 그대로 둬서 과거 CTR 집계 호환 유지)

계측 영역 8곳: 홈 마감레이더 / 키워드 / 우리아이 신규 / 비로그인 티저 / 추천픽 / 마감미정 · 탐색 그리드 · 내 레이더.

**왜 지금 하는가:** 유저가 적어도 **자리별 분포는 비율이라 일찍 수렴**한다.
나중에 (1) 배너·프리미엄 카드를 실제로 눌리는 자리에 꽂고, (2) B2B 상품화 때
"이 자리는 CTR N%" 라는 **단가 근거**로 쓴다. 나중에 만들면 과거 데이터가 없어서 못 판다.

### 4-4c. GA(GTM)로는 이걸 대체할 수 없다

현재 `GTM-PR2K864P` + Vercel Analytics가 **프로덕션에만** 붙어 있다(`layout.tsx:9-10`).

| | GA4/GTM | 우리 `events` |
|---|---|---|
| 체류시간 | 평균 참여 시간(포커스 중인 시간)만. 클래식 "time on page"는 GA4에 없음 | 미계측 (필요 시 추가) |
| 스크롤 뎁스 | 향상된 측정은 **90% 도달 1회**만 발생 → 분포 아님. 25/50/75는 GTM 스크롤 트리거를 따로 만들어야 함 | 미계측 |
| **영역·자리별 CTR** | 태그를 직접 짜면 가능하나 세그먼트 결합 불가 | ✅ `card_open` |
| **자녀 월령·가입 여부와 결합** | ❌ (GA는 우리 DB를 모름) | ✅ `user_id` 조인 |

> **결론: GA는 총량 참여도용, 자체 events는 상품화용.** B2B에서 팔 문장은
> *"6~12개월 부모의 마감레이더 3번 자리 CTR"* 인데 이건 GA로 못 만든다. 둘은 대체재가 아니라 보완재.
> 다만 **스크롤 뎁스는 GTM 스크롤 트리거로 25/50/75를 켜두면 코드 0줄**이라 먼저 해볼 값어치가 있다.

## 6. 성장스코어 / 등급제 — **인스타 없이 하는 법**

### 6-1. 먼저 사실확인 (보고서에서 가장 위험한 부분)

> **"마이페이지에 인스타 계정 연동 → 팔로워·반응률 분석"은 지금 대부분의 유저에게 작동하지 않는다.**
>
> - Instagram **Basic Display API 종료 (2024-12-04)**
> - 후속인 *Instagram API with Instagram Login* 은 **프로 계정(비즈니스/크리에이터) 전용**
> - 우리 타겟인 일반 육아맘 개인 계정은 **연동 자체가 불가**
>
> 이건 로드맵에 넣기 전 **반드시 Meta 개발자 문서로 재확인**할 것. 이 전제가 틀리면 §6 전체 설계가 바뀐다.

남는 선택지는 3개뿐이고, 검증 강도가 전부 다르다: (a) 자기신고, (b) 핸들 입력 후 공개 프로필 1회 조회(BD 사용 — 건당 비용·정책 리스크), (c) 스크린샷 인증(수동).

### 6-2. 등급제의 **더 큰 문제 — 다수를 소외시킨다**

엄빠레이더 유저 대부분은 인플루언서가 아니라 **그냥 부모**다.
"브론즈 엄마"라는 라벨은 **"나는 어차피 당첨 안 되겠네"** = 이탈 신호다.
게다가 사행성 금지·무보상 원칙과도 마찰한다.

### 6-3. 카드에 조건을 매기는 안(핏 태그) — **데이터 확인 결과 폐기** (2026-08-20)

초안에서는 "유저에게 등급을 매기지 말고 카드에 모집조건 태그를 매기자"고 제안했다.
**발행중 카드 361건 캡션 전수 확인 결과, 이 안은 성립하지 않는다.**

| 조건 유형 | 명시 비율 (n=361) | 판단 |
|---|---|---|
| **팔로워 수 조건** | **2건 (1%)** | 사실상 없음 |
| 팔로우 필수 | 203건 (56%) | 누구나 충족 → 필터 가치 0 |
| 공개계정 | 50건 (14%) | 너무 희소 |
| 릴스·피드 후기의무 | 45건 (12%) | 너무 희소 |
| 모집인원·선착순 | 34건 (9%) | 너무 희소 |
| 지역 제한 | 13건 (4%) | 너무 희소 |
| 배송비·자부담 | 11건 (3%) | 너무 희소 |
| **신청방법(DM/폼/댓글)** | **328건 (91%)** | 유일하게 보편적 |

> **왜 없는가:** 브랜드가 참여 모수를 최대한 늘리려고 **선정 기준을 내부에만 두기 때문.**
> 즉 조건 미명시는 데이터 누락이 아니라 **이 시장의 구조**다. 파서를 잘 만들어도 채워지지 않는다.
> 필터를 만들면 카드 대부분이 "정보 없음"으로 빠져 필터가 무의미해진다. → **폐기.**

### 6-3b. 그래서 얻은 더 중요한 결론 — 제품 방향이 바뀐다 ★

조건이 사전에 공개되지 않는다 = **유저는 "될지 안 될지"를 미리 알 수 없다.** 응모는 사실상 복권이다.
그러면 유저의 진짜 니즈는 **"될 만한 걸 고르기"가 아니라 "놓치지 않고 많이·빨리 응모하기"** 다.

| 버릴 방향 | 가져갈 방향 |
|---|---|
| 적합도 필터 / 등급 / 핏 스코어 | **마감 전 알림 · 응모 이력 관리 · 중복 방지** |
| "이거 나도 될까?" 를 예측 | **"놓친 거 없나?" 를 보장** |

**이게 이미 만든 것과 정확히 맞물린다:** 관심/신청함 체크(`user_post_status`) · 마감 D-day · 푸시(§5-2) · `/my` 내 레이더.
즉 §5의 1~3순위가 **더 강해졌다.** 새 기능을 만들 게 아니라 이 축을 두껍게 하는 게 맞다.

**그리고 조건이 안 적혀 있다는 사실이 곧 기회다.**
`ROADMAP-NEXT`의 "신청했어요 → 받았어요" 2단계 토글이 여기서 진짜 값을 갖는다 —
유저가 결과를 남겨주면 **브랜드별 실제 당첨률**이라는, 인스타 캡션엔 존재하지 않고 우리만 가질 수 있는 데이터가 쌓인다.
유저에겐 "이 브랜드 응답률 높음", 광고주에겐 지원자 풀 증거. **단 n=32에선 무의미 → G1 이후.**

### 6-4. 그래도 유저 스코어를 넣는다면 — **3단 사다리**

| 단계 | 데이터 소스 | 검증 | 언제 | 유저에게 보이는 것 |
|---|---|---|---|---|
| **1단 — 행동 배지**<br>(인스타 0) | 이미 있는 `user_post_status`(관심/신청함) + `events` | 완전검증 | **지금 가능** | "이번 주 3건 발견" · "첫 신청 완료" · "제보 채택" — **경쟁 랭킹 X, 개인 진척만** |
| **2단 — 자기신고 구간** | 가입 후 30초 선택 | 미검증 | G0 통과 후 | 팔로워 **구간**(비공개 / 1천↓ / 1~5천 / 5천~1만 / 1만↑). 핸들 안 받으므로 개인정보 부담 최소. **세그먼트 사이징엔 충분** |
| **3단 — 핸들 1건 검증** | 희망자만 핸들 입력 → BD 공개 프로필 1회 조회 → 30일 캐시 | 검증 | G1 이후 | "인증" 배지 + 프리미엄 매칭. 수집 동의·목적 명시 필수 |

**1단만으로도 B2B 세일즈 문장이 나온다:**

> "주 1회 이상 실제로 체험단 원문까지 이동하는 활성 부모 N명" — 팔로워 수보다 **광고주에게 더 설득력 있는 숫자**다. (지금 그 N = WQD)

### 9-3. 판정 기준 4개 (외부 제안이 오면 이 순서로)

1. **정책 5줄과 충돌하나?** (`OVERVIEW.md` §5) → 충돌이면 즉시 폐기
2. **우리 DB에 그 데이터가 실제로 있나?** → 없으면 폐기 (핏 태그가 여기서 걸렸다)
3. **현재 n에서 측정 가능한가?** → 불가면 보류 (D7 리텐션이 여기서 걸렸다)
4. **이미 만든 걸로 되나?** → 되면 최우선 (푸시·`user_post_status`가 여기 해당)

### 9-4. 다음에 외부에 물을 땐 — 컨텍스트를 먼저 줄 것
