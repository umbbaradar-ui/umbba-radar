## 1. 요약 (Executive Summary)

**한 줄 평가:** 코드 완성도는 "M2급"인데 사업 단계는 "M0(MAU 0)"인 제품 — **새로 만들 것이 거의 없고, 이미 만든 엔진을 켜고·타깃을 좁히고·공급을 안정화하는 것이 전부다.** 1인 운영 기준 구조·정책 가드레일·SEO/PWA·방어적 코딩 모두 출시 수준 이상이나, ①출시 전 막아야 할 보안 결함 2건과 ②리텐션 측정 자체를 막고 있는 미가동 채널(Web Push)이 발목을 잡는다.

**지금 가장 중요한 3가지:**
1. **Web Push VAPID env 2개 등록 + 재배포 (코드 0줄).** 이메일·SMS 영구 금지(정책③)라 Web Push가 유일한 복귀 채널인데 `push-service.ts`에서 fail-closed로 100% 잠겨 있다. 이게 꺼져 있으면 M2(D7 25%) 검증 자체가 불가능 → **사업 검증의 선행조건.**
2. **관리자 인증 재설계 (보안, 출시 전 필수).** 평문 비밀번호를 쿠키에 그대로 저장 + 브루트포스 무방비 + service_role 전권. 단일 자격증명 탈취 = DB 전권 탈취.
3. **타깃을 1개 페르소나("임신 후기~출산직후 첫째 부모")로 좁히고 그 세그먼트의 D7 25%를 증명.** MAU 숫자가 아니라 "좁은 세그먼트의 리텐션"이 증명 대상. 수익화는 전부 후행 변수.

**출시 가능 상태인가?** **조건부 가능.** 폐쇄테스트는 진행 가능하나, 프로덕션 신청(~6/18) 전에 **보안 P0 2건(관리자 인증·SSRF) + next 오픈 리다이렉트(피싱) 차단 + VAPID 점화**는 처리 권장. 나머지는 출시 후 데이터를 보며 순차 처리해도 무방하다. 기능적 차단 버그(크래시·데이터 손상)는 없다 — 검증된 버그는 대부분 "표시 정확성·미래 스케일링·심층 방어" 등급이다.

## 2. 사업성 분석 및 계획

### 2.1 시장 (저출산 리스크 포함)
- **저출산은 단기 리스크가 아니다.** 합계출산율이 2023년 0.72 저점 후 2년 연속 반등(2024 0.75 → 2025 0.80), 2025년 출생아 25.4만명(+6.8%). 향후 2~3년은 신규 부모 유입이 오히려 소폭 증가. → `docs/BUSINESS_MODEL.md` L170의 "시장 -2~3%/년 축소" 전제를 **"코호트 밀도 부족"**으로 정정 필요.
- **진짜 리스크는 시장 크기가 아니라 코호트 밀도** — 좁은 시기 세그먼트에서 "또래가 보일 만큼의 동시 활성"을 확보하기 어렵다는 점. 시장 매력도 자체는 "작지만 육아 초기 지출 집중 = 고가치 세그먼트"로 양호.

### 2.2 포지셔닝 (재검증 결과: moat 명제가 흔들림) ⚠️ critical
- **`BUSINESS_MODEL.md` L14·L74, `PROJECT_BRIEF.md` 5.5가 전제한 "외부 메타 큐레이션 = 우리만의 차별점"은 이미 다수 경쟁자가 점유 중.** 마더케이 멘토리(시기별 콘텐츠+체험단), 모아뷰(체험단 모아보기+필터+일일갱신), 베베프렌즈/베이비핫딜("핫딜 알림 No.1"), 맘플(체험단 1천만 참여), 베이비빌리(0년차 부모 30% 점유). "모아보기+시기매칭+알림"의 모든 축이 이미 누군가의 핵심기능이다.
- **방어 가능한 유일한 wedge = 중립성·커머스 비종속.** 멘토리=마더케이몰, 베이비빌리=빌리쇼핑은 자사 커머스로 기울 구조적 유인이 있다. **"브랜드몰에 종속되지 않은, 인스타 원문으로 바로 보내는 100% 중립 발견 미디어"**가 유일하게 방어 가능한 포지션.
- **경쟁자 표를 2분법→3분법으로 재작성:** ①시기매칭 큐레이션을 이미 하는 자(멘토리·베이비빌리) / ②모아보기만 하는 자(모아뷰·베베프렌즈) / ③본업이 따로인 자(맘카페).

### 2.3 해자(moat) — "데이터"가 아니라 "운영 일관성"
- `BUSINESS_MODEL.md` L30·L64가 해자로 본 "큐레이션DB·행동데이터·관계망"은 초기 해자가 아니다. DB는 같은 인스타·블로그 원천이라 복제 가능, 행동데이터는 MAU0에서 0, 관계망은 1인 영업 대역폭 한계.
- **실제 해자 = 신뢰 + 속도 + 일일 신선도.** M6 "Validated Moat"를 측정가능하게 구체화: "특정 세그먼트 D30 리텐션·NPS 경쟁앱 대비 우위 + 자발적 공유(맘카페·단톡)". **스폰서/광고 카드 비율 상한(예: 10%)을 자기규율로 명문화**(정책⑤ 보강).

### 2.4 수익모델 현실성
- 구조(B2B 리드→상단배너→스폰서카드)는 맞으나 **트래픽 없이는 전부 0인 후행 변수.** 초기 유일하게 현실적인 현금원은 `BUSINESS_MODEL.md` L132 "기존 브랜드 인맥과 직접 약식광고 10~30만원/건" — **"시스템"이 아니라 "운영자 인맥"에 달림.**
- **수익화 1순위를 디스플레이 광고(CPM 박함)가 아니라 "시기 세그먼트 스폰서카드"로.** 광고주가 가장 사고 싶은 건 "임신 28주 첫째 엄마에게 정확히 닿는 1장". **단가표(L151)는 MAU 근거 생기기 전 공개 금지(앵커링 손해).**
- **천장은 정책에 묶여 있다:** 본업전환(월250만+, MAU 5만 가정)은 베이비빌리·맘플이 점유한 시장에서 순수 큐레이션 미디어로는 구조적으로 어렵다. 천장을 올리는 유일한 길(하이브리드=프리미엄 슬롯 앱내신청)은 **절대정책①과 정면 충돌** → 정책 유지 시 부수입(월50~200만) 모델로 기대치 현실화. 이 트레이드오프를 `BUSINESS_MODEL.md`에 명문화해 자기기만 방지.

### 2.5 1인 운영 리스크 (공급 = 사업 연속성) ⚠️ high
- 수집이 인스타 쿠키(401)·세션밴·외부 키 정지(Gemini→네이버 OFF)에 의존. 미디어의 생명은 "매일 새 카드의 신선도"인데 **이 세 변수 중 하나만 깨져도 콘텐츠가 마르고 → daily loop·푸시·리텐션이 동시에 죽는다.** `OVERVIEW.md` L57·L75·L147.
- **공급 다변화를 사업 우선순위로 격상:** 브랜드 공식 RSS 화이트리스트(~30곳)·공공데이터포털 정부지원·체험단 sitemap을 Phase2 후순위→1순위로. 이들은 약관·세션밴 리스크가 없고 **인스타 의존↓는 "인스타 자동크롤링 영구금지"(정책②)와 정합.** + "카드 신선도 경보"(N일 신규0 → 운영자 알림).

### 2.6 KPI / 마일스톤 재정의
- **M1을 "MAU 100"이 아니라 "좁은 세그먼트 코호트 W1→W2 리텐션 25%"로.** 넓은 타깃("임신중~초등")은 어떤 세그먼트도 임계밀도 미달.
- 매출예측을 "연도"가 아니라 **"마일스톤 조건부"**로: M2 통과(D7 25%·클릭15%) → 광고영업 자격, M3(MAU1,000) → 첫 약식광고, M5(MAU1만) → 월100만+.

### 4.2 심각도 조정 각주 (원 주장의 과장/반증 부분)
1. **SSRF:** 취약점(필터 부재)은 실재하나 트리거 2곳 모두 `ensureAdmin` 뒤 → "비인증 사용자가 og:image만 심어 유발"은 반증. 제보(submitPostAction)는 extractFromUrl을 호출하지 않음.
2. **next:** 폼 미검증은 confirmed. 단 `auth/callback`·`confirm`은 `${origin}${next}` 문자열 결합이라 `//evil.com`이 자기 호스트 경로로 귀결 → "라우트에서 외부 유출"은 반증. 일관성·심층방어로 함께 적용 권장.
3. **Home limit:** "전량/전부 로드"는 부정확 — `repository.ts:37`에서 마감 지난 카드는 서버에서 이미 제외. "body 최대 2000자"는 DB 제약 아님(001:21 `body TEXT` 무제한). MAU0이라 미래 스케일링 이슈.
4. **Math.ceil:** 인용 라인 176→**177**(실제 위치). off-by-one은 라벨 오표기뿐 아니라 윈도우 경계 포함/제외에도 영향.
5. **ViewGate:** 메커니즘 모두 confirmed이나 우회는 soft paywall 의도된 동작이고 노출 콘텐츠는 공개 마케팅 본문. 깜빡임 원인은 마운트 위치가 아니라 SSR-후-클라리다이렉트 패턴. 중복 dedup은 `ViewGate.tsx:39`에 이미 존재.
6. **submitter_user_id:** 위조 행은 pending이라 공개 SELECT 미노출(001:70-72, 010:7), 뱃지 미구현(MAU0)이라 현 피해 없음.
7. **마이그레이션 유실:** 원 시나리오("같은 브라우저 로그인→로그아웃→재로그인")는 반증 — `MigrationOnLogin.tsx:23-24`의 per-(browser,userId) 1회 flag가 2차 마이그레이션 차단. 실제 유실은 교차기기에서만.
8. **proxy 루프:** "무한 리다이렉트 루프"는 반증 — `/signup/profile`이 EXEMPT라 루프 없음. 실제 영향은 "온보딩 고립"(가용성/UX).
9. **PII:** 헤드라인 반증 — `UserRow.tsx:33-45 ageLabel()`로 월령/세 요약만 노출, raw birth_date는 UI 미렌더. 삭제도 confirm() 1단계 존재.
10. **중복 발송:** "push twice → 2번 노출" 반증 — tag로 OS단 대체, 인용 라인 128은 루프 헤더(실발송 140).

## 5. 아키텍처·보안·성능

**총평:** 1인 운영 기준 매우 정돈됨. service_role 키 `import "server-only"` 격리(`supabase-server.ts:7`), 클라이언트 4종 분리, RLS 전 테이블 적용·본인 스코프, 외부 입력 전량 pending 진입(정책④ 준수), cron 시크릿 일관 검증, pg_trgm GIN 인덱스, 마이그레이션 트랜잭션+사후검증. SEO/PWA는 출시 수준 이상(카드 상세 JSON-LD schema.org Article **구현됨** — `post/[id]/page.tsx:106-134`).

### 5.1 보안 (우선순위 최상)

**P0 — 출시 차단급 (프로덕션 신청 전):**
1. **관리자 인증 재설계** (§4.1 1행, high). 순서: ①브루트포스 차단(IP 레이트리밋/실패 지연, 가장 실효적) ②평문 비번 쿠키 제거(HMAC 서명토큰) ③상수시간 비교. 4파일 검증 중복(ensureAdmin 2벌+layout+import-results)을 단일 헬퍼로 통합.
2. **SSRF 차단** (§4.1 2행). DNS 해석 기반 사설IP 거부 + og:image 동일검사 + redirect 수동처리 + 타임아웃. 검증을 extractFromUrl 내부로 일원화.
3. **공개 INSERT RLS 잠금** (보정 마이그레이션 020). 클라이언트 직접 insert 경로가 코드상 없으므로 정책 제거해도 기능손실 0 — 대용량 텍스트 스팸 벡터도 동시 차단.

**P0(보조) — next 오픈 리다이렉트** (§4.1). `safeNext` 유틸, 폼·라우트 전부 통과.

**P1 — 출시 직후:** 공개 쓰기 레이트리밋(track/제보/문의 + Turnstile + events TTL), PII 보강(birth_date는 이미 마스킹됨 — raw date RSC 페이로드 제거 정도).

### 5.2 성능
- **홈 피드 select(*) + limit 100** (§4.1, low). 즉시 가성비 최상 수정: `repository.ts:31`에서 body·search_keywords 제외하고 리스트 필요 컬럼만 명시 select(OWNERSHIP "본문 리스트 미노출" 근거, 위험0·노력0).
- **레이아웃 알림 비용** (§4.1, medium). `React.cache()`로 auth.getUser 4회→1회, 레이아웃은 배지 경량쿼리, posts select 최소화. (추가 발견: 홈 `page.tsx:42`도 getUserChildrenBirths 독립호출 → cache() 도입 시 함께 해소.)

- **Server Actions bodySizeLimit 10MB**: 클라이언트 업로드 전 리사이즈/압축, 대용량은 signed URL 직접 업로드.

### 5.3 확장성·운영 (MAU 증가 대비, 후순위)
- **Storage orphan 확정:** `curation/repository.ts:410-412` `deletePost`는 DB 행만 삭제하고 `storage.remove`를 호출하지 않음 → 카드 삭제 시 이미지가 버킷에 영구 잔존. 삭제 시 thumbnail remove 동반 + 주기 orphan 정리 cron.

| 9 | **공급 다변화 착수**(RSS·공공API 1순위) + 신선도 경보 | 인스타 단일장애점 해소 = 리텐션 붕괴 방지 | 중 | ✅ 인스타 의존↓는 정책② 정합 | 출시 직후 |
| 10 | **토스 미니앱 입점 신청** | 자력 1,000명보다 디스커버리 기대값↑ | 중 | ✅ 무관 | 출시 직후 |

**대기열(11~):** 공개 쓰기 레이트리밋 · 레이아웃 알림 비용 축소(React.cache) · 홈 피드 select 컬럼 최소화 · track 오발화 수정 · proxy fail-open · Storage orphan 정리 cron · "같은 시기 TOP5" 위젯.

## 8. 하지 말 것 / 주의

**스코프크립 (검증 전 금지):**
- MAU 1,000 전 유료광고 영업 — 근거 데이터 0 → 디스카운트·신뢰 소모.
- 단가표 공개 — 앵커링 손해.
- 넓은 타깃 유지 — 어떤 세그먼트도 임계밀도 미달, 리텐션 안 뜸.
- 풀 커뮤니티/게시판 — 1인 모더레이션 붕괴.
- 인스타 단일 공급 의존 지속 — 세션밴 1번에 콘텐츠 마름 → 리텐션 붕괴.
- 커플 연동·인스타 핸들 입력·제보 상단탭 복귀·전체 닉네임 스펙·금전 스테이킹 — 트리거 충족 전 동결.

**절대정책 위반 위험:**
- ① 앱내 신청처리 X — **하이브리드(프리미엄 슬롯 앱내신청)는 천장을 올리지만 정책①과 정면 충돌.** 본업전환을 노릴 때만 정책 예외로 *명시적 재논의*, 조용히 도입 금지.
- ② 인스타·틱톡 자동 크롤링 영구 X — 공급 다변화(RSS·공공API·업체동의 모니터링)는 정책 안전.
- ③ 이메일·SMS 영구 X — Web Push만. 푸시 빈도 주1~3회로 권한박탈 방지.
- ④ 자동 발행 X — 전건 관리자 승인 유지(현 코드 준수).
- ⑤ 광고 화면당 2개 이하·의료/금융/사행성 거부 — 상단 롤링배너는 한자리 순환이라 정합. 스폰서/광고 카드 비율 상한(10%) 자기규율로 보강.
- ⑥ 무료 티어 우선 — Sentry 무료·Upstash 무료·Vercel KV 등으로 충족.

**운영 주의:**
- 구조 본질을 바꾸는 작업(020 마이그레이션, /my 게이트 정책, ViewGate 한도)은 **반드시 사전 공유.**
