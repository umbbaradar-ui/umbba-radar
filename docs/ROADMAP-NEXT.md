## 1. 사용자가 던진 4개 아이디어 — 판정

### 1) 제보 시스템 → **메인 동선에서 강등 (삭제 X)**
- 판정: 동의. MAU 0에서 제보량 기대 못 함. GNB 한 칸 가치 없음.
- 단 **삭제가 아니라 강등**: 모바일 하단탭에서 빼고 "더보기" 시트로(이미 거기 있음), 데스크탑 상단도 빼기. 카드 상세 하단 "정보 틀렸어요/제보" 정도로.
- 이유: 나중에 "사용자 참여" 신호로 쓸모 생김. 코드는 두고 눈에서만 내림.
- 작업량: 소.

### 2) 인스타 계정명 수집 / 부분 연동 → **❌ 안 함 (보류)**
- 판정: 반대. 사용자도 "목적 불명확" 인정 = 그게 정답.
- 근거: ①목적 없는 개인정보 수집은 Play 데이터보안 항목·심사 변수만 늘림 ②인스타 API 부분연동은 비즈니스 인증·앱심사 필요(1인 운영 과함) + "인스타 자동 크롤링 영구 금지" 정책과 충돌 ③받아서 쓸 곳이 없음.
- 결론: 쓸 목적이 명확해지면 그때 재논의. "받아두면 언젠가"식 수집 X.

### 3) 부부 초대/공유 (아내↔남편) → **알맹이(바이럴)만 살리고, 시스템(연결)은 보류**
- 처음엔 가장 유망해 보였으나 **"주 사용자 엄마 90%"가 판도를 바꿈**:
  - 부부 "연결/매칭/권한/알림" 시스템은 **아빠 참여에 의존** → 엄마 90%면 10%만 쓰는 기능에 큰 공수 = 리스크.
- **핵심 통찰**: 부부의 바이럴 효과(한쪽이 다른 쪽 끌어옴)는 **"카드 공유 버튼"만으로 80% 달성**됨. 연결 불필요.
  - 엄마가 "남편한테 보내기 💌" 버튼 누르는 순간 = 그게 곧 부부 협업.
- **"부부"는 기능(시스템)이 아니라 메시지(마케팅)로 살린다** — 앱 이름 "엄빠레이더"·슬로건 "엄빠 대신 스캔"을 공유 버튼 카피로.
- 정책 주의: "부부가 같이 **신청**"(X, 앱 내 신청 처리 금지) 아니라 "부부가 같이 **발견·공유**"(O)로 프레이밍.
- 결론: **공유 버튼(3-1단계)은 GO. 부부 pairing(3-2단계, 초대·관계DB·알림)은 보류** — 출시 후 아빠 사용 데이터 보고 재결정.

### 4) 부부·육아 커뮤니티 → **방향만. "엄마 중심"으로 조정. 한참 뒤(Phase 3+)**
- 원칙: 커뮤니티를 통으로 만들면 망함(1인 운영 → 스팸·분쟁·CS 폭증). **카드에 종속된 가벼운 참여**부터.
- "엄마 90%" 반영 → 부부 그룹이 아니라 **"비슷한 월령/지역 엄마들"** 중심.
- 진화 순서:
  - **Phase A (씨앗)**: 카드별 "후기 한 줄"("신청했어요/받았어요" 체크 + 별점). 부담 0, 신뢰 신호 + 큐레이션 강화.
  - **Phase B (대화)**: 후기에 1뎁스 댓글("어떻게 신청?"). 닉네임.
  - **Phase C (관계)**: 비슷한 월령/지역 엄마 그룹 추천.
  - **Phase D (자생)**: 주제별 게시판 — 여기부터 신고·모더레이션 필수.
- 콜드스타트 해법: 빈 게시판 아니라 **"카드"가 떡밥**("이 협찬 받아본 사람?"). 카드 중심으로 대화 붙게 설계.

#### 닉네임 정책 (2026-06-02 결정) — **지금은 익명 유지**
- 결정: 사용자 닉네임은 **커뮤니티(후기 Phase A)와 함께** 도입. 지금은 익명.
- 근거: MAU0 + 커뮤니티 없음 → **닉네임이 보일 곳이 없음**. 미리 받아도 입력 동기 약함(부부연결 보류와 같은 논리).
- 그릇은 이미 있음: `user_profiles.display_name`(009), `posts.submitter_handle`(005, 제보 1회성). 테이블 추가 불필요.
- **유니크 닉네임은 신중**: 중복방지+실시간체크+변경정책+금칙어 필터까지 = 무게의 90%. 커뮤니티 만들 때 제대로 설계할 것. 지금 미리 X.
- 도입 시점: 후기(Phase A)에서 "○○님"이 실제 노출될 때. 그때 `display_name`에 유니크 부여 + 입력 UI.

### 5) 제보 디테일 강화 (2026-06-02 추가 방향) — 두 갈래로 분리

> ⚠️ 아래 A·B는 성격이 완전히 다름(B2C 참여 vs B2B 리드). 절대 섞지 말 것.

#### A. 제보 게이미피케이션 — "많이 제보하면 뱃지/로고" (B2C, 커뮤니티와 함께)
- 아이디어: 인스타 이벤트를 많이 제보한 사용자에게 커뮤니티에서 쓸 **뱃지/타이틀/로고** 부여.
- **데이터 기반 이미 있음**: `posts.submitter_user_id`(005 마이그레이션) → "누가 몇 건 제보·채택됐나" 집계 지금도 가능. 뱃지용 데이터는 이미 쌓이는 중.
- **지금 안 만드는 이유**: 뱃지는 "보여줄 곳(커뮤니티 프로필·후기 옆)"이 있어야 의미 → 커뮤니티 Phase 3. MAU0엔 제보 거의 없음.
- **방향(확정)**:
  - **채택된 제보만 +1** (관리자가 published 한 제보) — 스팸 방지. 단순 제출은 카운트 X.
  - 등급 예시: 🌱새싹 → 🐻단골 → 👑레이더마스터 (건수 기준은 운영데이터 보고).
  - 노출 위치: 커뮤니티 프로필 + 후기(Phase A) 옆.
  - **커뮤니티 Phase A(후기 한 줄)와 묶어서 설계** — "제보 N건 + 후기 N건 → 등급" 일관성.
- 시점: 커뮤니티 Phase 3과 함께(먼 미래). 지금은 방향만.

#### B. 업체용 B2B — 3단계 진화 (2026-06-02 확장)

> 무료 리드 수집 → (사업자등록 후) 유료 프리미엄. 순서가 중요: 리드 풀을 먼저 쌓아야
> 유료 팔 때 영업 대상이 생김.

**B-1. 입점/상품/제휴 요청 폼 — B2B 리드 수집 (출시 후, 무료)**
- 업체/브랜드가 "체험단 올려주세요(입점)" / "상품 추가요청" / "제휴 제안"을 **DB로 받기**.
- A(B2C)와 별개 트랙: 대상이 **업체**. 수익화 씨앗(향후 CAMPAIGN 담당자 리드 풀).
- "받기"는 가볍게 OK / "처리(심사·계약·정산)"는 사업자등록 후.
- 인스타 계정 수집(2번 보류)과 다른 점: 목적 명확(업체 리드) → 받을 가치 O.
- MVP: `/business`(또는 `/partner`) — 업체명, 담당자, 연락처, 인스타·홈페이지 URL,
  요청유형([입점][상품추가][제휴][인스타 모니터링]), 한 줄 메시지.
  `business_inquiries` 테이블(status: new/contacted/done) + 관리자 목록 + 텔레그램 알림(재활용).

**B-2. 업체 인스타 계정 공유 — 수집 채널 확장 (B-1 폼에 흡수, 출시 후)**
- 업체가 "우리 인스타에서 이벤트 자주 올려요, 모니터링 해주세요" 하고 **자기 계정 제출**.
- **기존 시스템과 직결**: A루틴이 `instagram_accounts`(현 202개) 모니터링 중 →
  업체 제출 → **관리자 승인 → 그 목록에 추가** = 수집 소스가 업체 자발적으로 늘어남(운영부담↓, 카드↑).
- 별도 시스템 불필요: B-1 요청폼에 `[인스타 모니터링 요청]` 유형 추가 + 인스타 URL 받으면 끝.
- **정책상 오히려 안전**: "인스타 자동 크롤링 영구 금지 / A루틴은 더미계정 제한 모니터링만" 원칙에서,
  업체가 "내 계정 모니터링 동의"하는 건 무단 크롤링 아니라 **업체 요청 기반** → OK.

**B-3. 프리미엄 판매 영역 — 수익화 (사업자등록 후, 유료) 💰**
- 업체가 돈 내고 사는 것: **프리미엄 링크 영역 / 상단 고정 노출 / 스폰서 카드** 등.
- B-1·B-2와 무게 다름: 실제 **결제·정산·세금계산서 = 사업자등록 필수**.
- 이미 자리 있음: OWNERSHIP의 ADS(`AdSlot` placeholder)·monetization 모듈, "사업자등록 후 활성화".
- 정책 준수: 화면당 광고 2개 이하, 의료·금융·사행성 거부.
- **지금은 설계 메모만**. 구현은 사업자등록 + MAU 확보 + 광고정책 확정 후.
- 전략: B-1로 모은 "관심 업체 리드"에게 사업자등록 후 바로 영업 → 리드 없이 유료부터 X.

  **B-3-a. 상단 롤링 배너 판매 (2026-06-03 구체화) — B-3의 1순위 실현 형태**
  - 아이디어: 메인 최상단 `AdSlot id="top_banner"`를 **롤링 캐러셀**(스폰서 배너 3~5개 자동 슬라이드)로 만들고, 각 슬롯을 **업체에 판매**(배너 이미지 + 클릭 링크).
  - **토대 이미 있음**: `top_banner` placeholder가 메인 헤더 아래 박혀있음(`DiscoveryView`). 롤링 컴포넌트로 교체만 하면 됨. `reservedHeight`로 layout shift 방지도 설계됨.
  - **정책 안전**: 롤링은 한 자리에서 순환 → 화면엔 1개만 보임 → "화면당 2개 이하" 준수.
  - **파이프라인 완성**: B-1 업체폼 리드 → 사업자등록 후 "상단 배너 1주 N원" 영업 → 여기 노출. 리드→판매→노출 자연 연결.
  - 필요 시스템(구현 시): `ad_slots`/`sponsors` 테이블(배너URL·링크·노출기간·우선순위), 관리자 등록 UI, 노출/클릭 카운트(업체 리포트용 — ANALYTICS 재활용), 캐러셀 컴포넌트.
  - 시점: 사업자등록 + MAU 확보 후. 지금은 자리(placeholder)만 유지.

시점: B-1·B-2는 출시 후(무료, 독립적, 커뮤니티 안 기다림). B-3은 사업자등록 후.
