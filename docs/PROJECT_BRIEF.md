# 육아 혜택 큐레이션 웹앱 — 프로젝트 브리프

> 마지막 업데이트: 2026-05-21
> 본 문서의 목적: 바이브 코딩 진행 중 AI 어시스턴트에게 프로젝트 컨텍스트를 한 번에 전달하고, 개발자(본인)가 방향이 흐려질 때 돌아올 기준점을 만든다.

---

## 1. 한 줄 소개

흩어져 있는 육아 관련 협찬·리그램·추첨·무료체험 정보를 한곳에 모아, 부모가 **놓치지 않고 신청**할 수 있게 해주는 웹앱.

## 2. 타겟 사용자

- 1차: 임신 중 ~ 출산 직후 부모 (혜택 정보에 가장 민감한 시기)
- 2차: 영유아 ~ 초등 자녀를 둔 부모
- 지역: 한국

## 3. 컨셉 / 톤

- 컨셉 방향: "좋은 부모되기" 보다는 **행동 유도형** ("놓치지 말고 신청하기")
- 톤: 실용적, FOMO 자극, 간결
- 메인 메시지 후보: *"출산 전에 신청 안 하면 못 받는 것들, 다 모았어요"*
- 서비스 이름: **엄빠레이더** (확정)
- 슬로건 후보: *"놓치는 혜택은 없게"* / *"부모님 대신 스캔 중"* / *"오늘의 혜택을 잡아두는 안테나"*
- 이름 채택 이유: **"레이더"** = 능동적으로 스캔해 결과만 보여주는 도구 → 큐레이션 서비스의 본질("대신 훑어준다, 당신은 확인만")과 정확히 일치. **"엄빠"** 는 공동육아 트렌드를 반영해 엄마·아빠 모두 포섭.

## 4. 핵심 가치 제안

1. **모아보기** — 인스타·블로그·웹에 흩어진 혜택을 한 페이지에서
2. **시기별 큐레이션** — "내 아이 월령에 지금 필요한 것"만 보임
3. **개인 체크리스트** — 로그인하면 신청함/관심 표시, 마이페이지에서 추적
4. **마감일 관리** — D-day 배지로 임박한 것 우선 노출

## 5. Phase 로드맵

### Phase 1 — MVP 출시 (지금 만들 것)
- **데이터 수집: 본인이 직접 큐레이션**
- 관리자 페이지에서 인스타 링크·이미지·정보를 붙여넣고 발행
- 사용자 기능: 열람 + 필터 + 로그인 + 신청/관심 체크

### Phase 1.5 — 토스인앱(앱인토스) 포팅 (PWA 안정화 후)
- **자체 PWA로 콘텐츠·UX 검증 → 동일 백엔드를 그대로 둔 채 토스 미니앱으로 이식**
- 토스 정책: 사업자 등록 없이 입점 가능 (2026년 기준), 영업일 2~3일 검수
- 토스 누적 가입자 ~3,000만 도달 풀, 부모 타겟과 매칭 양호
- 자체 PWA는 메인 채널로 계속 유지 (브랜드·SEO·실험 자유). 토스는 보조 배포 채널
- 사업자 필요 기능(토스 페이·인앱 광고 등)은 사업자 등록 시점인 Phase 3에서 활성화
- 참고 사례: 안전집사(프롭테크 큐레이션) 토스인앱 입점 후 신규 고객 99% 토스 유입, 월 매출 40배

### Phase 2 — 자동 수집 (출시 후, 트래픽 모이면)
- **광범위 스크래핑 금지** (약관 위반·계정 차단 리스크)
- 안전한 방식: 본인이 신뢰하는 브랜드 공식 페이지·블로그 ~30개를 화이트리스트로 등록
- 매일 새 글을 자동으로 가져와 **"승인 대기함"** 에 적재
- 본인이 5분 훑고 "이건 이벤트 → 발행" 클릭 (자동 발행 아님)

### Phase 3 — 사용자 제보 (유저 베이스 생긴 뒤)
- 사용자가 발견한 혜택을 링크로 제보
- Phase 2의 **동일한 "승인 대기함"** 으로 흘려보냄 → 시스템 통합
- 채택 시 제보자 닉네임 표기 (게이미피케이션 여지)

## 5.5 전략적 갈림길 — 미디어 vs 플랫폼

향후 가장 큰 의사결정 지점은 **"앱 내 신청을 받을 것인가"** 다. 이는 단순한 기능 추가가 아니라 회사의 정체성 결정이다.

| 축 | A. 큐레이션·미디어 | B. 신청 처리·플랫폼 |
|---|---|---|
| 우리 역할 | 정보 모아주는 미디어 | 신청을 처리하는 마켓플레이스 |
| 사용자 흐름 | 카드 → 외부 인스타에서 신청 | 카드 → 앱 내 폼 작성 → 우리가 브랜드에 전달 |
| 우리의 차별점 | **이것 자체가 차별점** ("외부 메타 큐레이션") | 멘토리·레뷰와 동질화 |
| 수익 모델 | 광고·노출비 (CPM/CPC) | 신청 건당 수수료·구독료 |
| 운영 부담 | 낮음 (수집·발행만) | 높음 (CS·개인정보 위탁·배송 분쟁) |
| 법적 부담 | 거의 없음 | 개인정보처리 위탁·전자상거래법 일부 적용 |
| 천장 (수익 잠재력) | 중간 | 큼 |
| 1인 가능 여부 | 가능 | 불가능 (영업·CS 인력 필요) |

**선택:** Phase 1~2는 **순수 큐레이션(A)** 으로 간다. 이게 우리 차별점이고, 1인 운영이 가능한 유일한 형태다.

**Phase 3 이후 하이브리드 가능성:** 외부 큐레이션은 그대로 유지하되, **돈을 낸 브랜드만 "앱 내 원클릭 신청" 프리미엄 슬롯**으로 부분 확장. 비유: 배민·요기요가 모든 식당을 리스팅하되 광고비 낸 식당만 상단·프리미엄 노출 받는 것과 동일.

**Phase 3 신청 기능 검토 트리거 (아래 중 2개 이상 충족 시):**
- [ ] 월 활성 사용자 (MAU) 5,000명 이상
- [ ] 광고·노출 모델 수익이 정체 (월 매출이 평탄해짐)
- [ ] 브랜드 측에서 *먼저* "우리 캠페인을 너희 앱에서 받을 수 있냐" 문의 누적 5건 이상
- [ ] 사용자가 "그냥 여기서 한 번에 신청하면 안 되냐" 피드백 반복
- [ ] 풀타임 전환 또는 동업자 확보

이 트리거가 충족되기 전까지는 절대 만들지 않는다. 기술적 확장 방식은 `ARCHITECTURE.md` 의 "계획된 확장 — Application 부서" 참고.

## 11. 바이브 코딩 시 AI에게 알려줄 핵심 요약 (한 단락)

> 서비스 이름 **엄빠레이더**. 임신·출산·육아 관련 협찬/리그램/추첨/무료체험 정보를 한곳에 모아 부모가 놓치지 않고 신청하게 해주는 웹앱이다. 컨셉은 "능동적으로 스캔해 결과만 보여주는 큐레이션" — 사용자는 외부 인스타·블로그 링크로 가서 신청한다 (앱 내 신청 ✗, 미디어 포지션 유지). Next.js + Supabase + Tailwind + shadcn/ui 스택으로 Vercel 배포. Phase 1은 자체 PWA로 본인이 직접 큐레이션하는 MVP, Phase 1.5에서 토스인앱(앱인토스)에 미니앱 형태로 보조 배포한다 (백엔드 공유, UI만 별도). 사용자는 구글 로그인 후 카드별로 "신청함/관심" 체크 가능. 시기 카테고리(임신중~초등)와 유형 태그(리그램/추첨/무료체험/협찬/정부지원)로 필터링한다. 자동 크롤링은 절대 광범위하게 하지 않으며, Phase 2의 화이트리스트 자동 수집과 Phase 3의 사용자 제보는 모두 "승인 대기함"을 거쳐 본인이 승인한 것만 발행한다.
